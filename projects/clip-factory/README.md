# clip-factory —— 数据卡工厂

一组数据点进去，四张 1080×1920 出来。

四张卡不是四份手写文案，是从 `src/points.js` 同一组数字算出来的：
成绩卡、对手卡、分段卡、汇总卡各看一个角度，改一个数四张一起变，不可能出现「成绩卡改了、对手卡忘了改」。

---

## 怎么跑

```
node build.mjs
node tests/gate.mjs
node tests/visual.mjs
node tests/fonts.mjs
node tests/download.mjs
node tests/ascii.mjs
node tests/shot.mjs
```

`tests/download.mjs` 会真的点「导出全部 4 张」，数浏览器收到几次 download。这一条别的测试替代不了。

换数据：编辑 `src/points.js`，重新 `node build.mjs`。

---

## 四张卡

| id | 抬头 | 中间那块画什么 |
|---|---|---|
| `result` | 本场成绩 | 150px 的大数字 + 一把 1.000–1.100 的尺，尺上两个刻度分别是上次和这次 |
| `rival` | 两条线 | 两根横条，越长 = 用时越短，我们橙色、对手灰色 |
| `split` | 20 m 分段 | 四根竖条，最高的那段标橙，每根下面标占比 |
| `sheet` | 本场全量 | 四个关键数并排 + 六项来源 |

四张共用同一副骨架：顶部死区 → 抬头 → 三列（车号/日期/车卡）→ **中间那块** → 五行表 → 汇总条 → 页脚。变的只有中间 496–832 那 336px。

---

## 数据点自洽是门禁在管

`src/points.js` 里这几个数必须互相说得通：

```
splits 相加      = time        （0.286+0.259+0.251+0.246 = 1.042）
prev             > time        （1.062 > 1.042，"快了 0.020" 才成立）
rival.time       > time        （1.061 > 1.042，"领先 0.019" 才成立）
```

`selfTest()` 每次跑都验这三条。改成对不上的数，卡片不会报错，但门禁会挂——因为「快了 0.020 s」这种话一旦和数据不符，就是硬造数字。

## 批量导出是怎么做的

```js
async function downloadAll() {
  for (const c of CARDS) {
    const b = await blobOf(c.id, 1080, 1920);
    download(b, `clip-factory-${c.id}-1080x1920.png`);
    await new Promise(r => setTimeout(r, 320));
  }
}
```

一张一张出、一张一张发，中间等 320ms。不等的话后一次 `a.click()` 会把前一次的下载顶掉，浏览器只落盘最后一张。

`tests/download.mjs` 就是来抓这个的：它监听 `download` 事件，要求正好 4 次，文件名四个都不同，而且四张 id 都得出现。实测四次全到。

---

## 门禁在查什么

通用部分在 `tests/core.mjs`：7 条禁用 API 静态扫描、5 个运行时插桩计数器必须全 0、导出 PNG 魔数 + 字节数、无外站资源、无外网请求、两张截图。

本项目自己的：

| # | 断言 |
|---|---|
| 1 | 4 张卡、id 不重复、默认是 result、画布 1080×1920、`selfTest()` 通过 |
| 2 | 分段合计 = 1.042、快过上次 0.020、领先 0.019、最快分段下标在 0–3 |
| 3 | **四张各出一遍 PNG，FNV 哈希必须四个都不一样** |
| 4 | 每张单独选中，墨量都 ≥ 8%，且四张之间最大最小差 ≥ 1%（否则说明没真画不同内容） |
| 5 | 切到 split，当前卡跟着变；同一时刻只能有一个芯片是按下状态 |
| 6 | 刷新之后回到 result |

第 3 条是这个项目最关键的一条。没有它，`BODY` 里四个函数全 `return` 一个空画布也能过——四张都是 4096 字节以上的合法 PNG。所以这里比的是整份 blob 的 FNV-1a 哈希，四张必须分开。

## 实测

| 项 | 值 |
|---|---|
| `dist/app.js` | 18 KB |
| 四张卡 | result 131 KB / rival 124 KB / split 122 KB / sheet 125 KB |
| 竖版 1080×1920 | 131 KB |
| 封面 1080×1350 | 106 KB |
| 安全区整体墨量（result） | 14.65% |
| 逐张墨量 | result 15.0% / rival 20.4% / split 27.4% / sheet 13.4% |
| 安全区 150px 连续死区 | 0 处 |
| 页面用到的不同字符 | 142 个 |
| MONO / DISP 各查 | 142 字，缺 0 |
| 门禁静态规则 | 7 条，0 命中 |
| 全程网络请求 | 8 条，全部本地协议 |
| 连续导出实测 | 4 张，文件名互不相同 |

这是五张卡里墨量最低的一套。`result` 是「一个大数字 + 一把尺 + 五行表」，本来就比满屏表格空；`sheet` 更低，13.4%。

`tests/fonts.mjs` 靠拦截 `fillText` 收集字符，只画默认那张的话另外三张的字根本不会被检查。所以 `preview()` 里先把四张都 `compose()` 一遍再停在第一张。

## 已知缺陷

1. **四张共用一副骨架。** 只有中间 336px 不同，抬头、三列、五行表、汇总条、页脚一模一样。连着发四条，一眼能看出是同一张卡换了字。想更像四条独立内容，得让骨架本身也跟着变。

2. **只有一组数据点。** 想发上一场，得改 `src/points.js` 再 `node build.mjs`。没有多组切换，也没有「导入 JSON」。一周要发三条就得来回改文件。

3. **四个分段是手填的。** 不是从计时器导出来的，而且必须刚好加起来等于总用时（门禁会拦）。真实计时带进位误差，手填四段一次凑准并不容易，凑不准就只能改总用时。

4. **成绩卡的大数字按字符硬切。** 150px 的数字拆成两段画：整数位在 x=60，小数位硬编码在 x=138。用时是 `1.0xx` 的时候刚好；哪天变成两位数秒（`2.042`），两段会叠在一起。20 m 直线跑不出两位数，所以现在是潜伏的，不是已发生的。

5. **汇总卡最空。** 13.4% 墨量，五张卡里最薄的版面。四个关键数只占 176px 高，下面五行表又短。

6. **对手条差别太小。** 归一化基准 `REF = 1.600` 是写死的，两条都接近满宽，实际差 3–4 个百分点宽，远看几乎一样长。把比例尺调大能让差距显眼，但那等于把「领先 0.019 s」画成「领先一大截」——不诚实。现在选了诚实这一头，代价是图上看不出赢。

7. **批量导出靠硬等。** 每张之间 `setTimeout(320)`，这个数是拍脑袋定的。慢机器上还是可能被吞。浏览器没给「上一次落盘了没」的接口，所以只能等。真出问题的话表现是「点了导出全部，结果只下来两三张」。

8. **批量只出 9:16。** 想要四张 4:5 封面得一张张点，没有「导出全部封面」。

9. **4:5 封面切掉眉标。** 封面居中裁切，取源图 y 285–1635，y=240 的橙色短杠和 y=276 的 `STEM RACING` 不在封面里。

10. **没有自动换行。** 所有文案都是单行硬编码，赛事名一长就按 `cut()` 截断加省略号，不会折行。
