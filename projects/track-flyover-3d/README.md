# track-flyover-3d · 20 m 直线赛道三维漫游

把 20.00 m 的直线赛道做成一个能用鼠标拖着看的三维场景，相机跟着车跑，五道计时门各报一次分段。

做它是因为我们讲「车为什么慢」的时候，一直缺一个能把**距离**和**时间**摆在同一张图上的东西。说「快了 8 ms」没有体感，但说「最后 5 米速度从 17.275 掉到 16.906」就有了。

## 怎么跑

双击 `index.html`。

不用起服务器，不用装依赖。`dist/app.js` 是已经打好的 IIFE 包，`file://` 下直接能跑。

改了 `src/main.js` 之后要重新打包，否则页面跑的还是旧代码：

```
node build.mjs
```

## 怎么做的

### 速度剖面换过一次模型

以前这里用单指数 `v(t) = v∞(1 − e^(−t/τ))`，τ 和 v∞ 由「1.230 s / 19.93 m/s」这对数反解。

那个做法是错的，而且错在两处。

第一处，形状不对。单指数是「推力一直作用、速度渐近逼近 v∞」，曲线单调上升，**跑不出峰值之后下降**。真车是 CO₂ 气瓶烧 110 ms，之后全程滑行减速。拿单指数去套，反解时要把中间变量 z 推到 200 以上才勉强收敛——一个正常的参数不会在那种量级上收敛，这本身就在说「这对数字不是这个模型长出来的」。

第二处，「1.230 s / 19.93 m/s」这对数算术上讲不通。20 m 跑 1.230 s，平均速度就是 16.26 m/s。推力只有一百来毫秒，之后一路减速，**末速必须低于平均速度**。19.93 > 16.26，不成立。

所以这一轮把剖面换成和其余项目同一套「脉冲 + 滑行」积分，RK4，`dt = 1e-5`，冲线那一步在区间内线性插值（不插值的话终点时间会被 dt 量化）。

```
F(t) = F_peak · sin(π t / t_burn)          0 ≤ t ≤ t_burn
F(t) = 0                                    t > t_burn
D    = ½ ρ Cd A v²
R    = Crr · m · g
m_eq = m + 4·I_wheel / r_wheel²
a    = (F − D − R) / m_eq
```

`m_eq = 0.065 + 4 × 4.5e-7 / 0.011² = 0.079876 kg`。轮子跟着转要吃掉一部分推力，等效质量比静质量大 23%。

积出来的三个数：1.1885 s / 16.906 m/s / 峰值 18.347 m/s。门禁锁的就是这三个，容差分别是 2e-3 s 和 5e-3 m/s。

「1.230 s / 19.93 m/s」作废，这一版不用它。

### 分段成绩

五道门的时间由 `tAt(x)` 反解：`x(t)` 在 0..T 上单调，二分 60 次，精度到 1e-12 量级。

模型积出来的分段（这些是算的，不是跑的）：

| 位置 | 时间 | 速度 |
|---|---|---|
| 5.00 m | 0.3293 s | 18.035 m/s |
| 10.00 m | 0.6095 s | 17.652 m/s |
| 15.00 m | 0.8959 s | 17.275 m/s |
| 20.00 m | 1.1885 s | 16.906 m/s |

峰值 18.347 m/s 出现在 0.1098 s，也就是燃尽那一刻，位置在 1.007 m。之后全程减速，最后 5 米掉了 0.369 m/s。

门禁只验「五道门的时间严格单调递增」，不锁上面这些具体数值——分段是积分的结果，锁死了反而会把积分参数焊住。

### 坐标和相机

场景单位就是米，1:1，没有缩放。

相机是 `PerspectiveCamera(42°, 1080/424, 0.005, 120)`。焦距那一项不是 9:16 的 0.5625——因为 3D 只渲染中间一条横带，见下面的已知问题。

相机位置沿赛道插值，`state.progress` 从 0 到 1 对应 0 到 20 m。进度是按真实车速推进的，再乘慢放系数：

```
progress += (v_now / L) · slow · dt
```

`slow = 0.25` 表示 1.1885 s 的实跑被拉成 4.75 s 播放。

### 2D 叠字

3D 跑在一个离屏 canvas 上，`compose()` 每帧把它整块画到展示 canvas，然后在上面叠文字和标注，导出的就是这个展示 canvas。屏幕所见和导出是同一批像素。

- 峰值时刻必须落在燃尽区间 0.09–0.13 s

## 已知问题

1. **屏幕上那个「起步峰值 a₀」显示的是负数。** `compose()` 里 `const peakA = aAt(0)`，标签写 `['起步峰值 a₀', ...]`，显示 `-0.1 m/s²`。因为半正弦推力在 t=0 时 `sin(0)=0`，起步那一瞬间只有滚阻和阻力，车是在**微减速**。真正的峰值加速度是燃烧中点的 262.5 m/s²，门禁验的也是那个。标签和取值的含义对不上，改法是取 `aAt(t_burn/2)`。

2. **`index.html` 侧栏还挂着旧模型的文案。** 那里写着「1.230 s / 19.93 m/s 是队内实测，不是估的」和「v(t)=v∞(1−e^(−t/τ)) 的 τ、v∞ 由这两个点反解」。模型已经换掉了，这段是静态 HTML，`main.js` 里没有任何代码写 `.note`，所以它会一直显示在页面上。这是这一轮改动漏掉的地方。

3. **21 N 和 110 ms 都是估的。** 代码里两个值都标了 `[VERIFY]`，意思是队里从来没实测过。整个速度剖面——包括门禁锁死的 1.1885 s / 16.906 m/s / 18.347 m/s——全部建立在这两个估的数上。换一组推力参数，结论会整体平移。真正要验得拿发射器和测力台做一次。

4. **半正弦推力在 t=0 时为 0，真车不是这样。** CO₂ 气瓶戳破膜片是接近阶跃的升压，几百微秒内就到峰值。半正弦只是个「起止时刻都连续」的方便形状，物理上并不对应真实压力曲线。代价就是起步瞬间车先微减速 0.06 m/s²，然后才开始加速。

5. **慢放系数 0.25 是拍的。** 界面上能拖到 0.05–1.00，但 0.25 这个默认值没有按镜头语言算过——没有「一秒素材里该看到多少米」的推导，就是试了几个值觉得看得清。

6. **3D 只渲染中间 424 px 一条横带。** `BAND = { y0: 668, y1: 1092 }`，画布其余部分每帧先用墨色 `fillRect` 盖死，再叠 2D 层。好处是相机可以用宽银幕比例、画面不被竖直拉扁，代价是上下那 1496 px 里一个三维像素都没有。

7. **跑道宽 0.180 m 标着 `[VERIFY]`。** 这个数从 Day 1 就在，没人拿卡尺量过。它影响的是俯视镜头里轨道和车宽的视觉比例，不影响速度。

8. **`dist/app.js` 是构建产物，但签进了仓库。** 571 KB。改完 `src/main.js` 忘记 `node build.mjs`，页面会安静地跑旧代码，而且没有任何提示。门禁是从 `dist/app.js` 跑的，所以门禁绿了也不代表源码改对了——这一点很容易骗过自己。

9. **`src/reel-export.js` 和 `design-tokens.css` 每次构建都会被覆盖。** `build.mjs` 开头无条件从 `../../shared` 拷这两个文件过来。在项目里直接改这两份，下次 build 就没了。

10. **门禁里的 `REF.a0 = 262.9` 和它实际打印的 262.5 不是同一个东西。** 门禁取的是 `profileAt(0.055).a`，燃烧中点，已经含阻力项和滚阻项，所以比理论值 `F/m_eq = 262.91` 低 0.4。容差给了 1.0 才盖住。哪天推力参数变了、阻力项变了，这个 0.4 会动，容差就成了隐形的。
