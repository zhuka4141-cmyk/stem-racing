# 闪灯反应计时 · Reaction Trainer

等灯，闪灯瞬间开表，点到就停。跑满五次出平均、最快、最慢，再导出成一张 1080×1920 的成绩卡。

这是车队内容计划的第 04 期。纯静态网页，双击 `index.html` 就能开，不联网，不上传任何数据。

上一期（`head-to-head`）算的是两台车差 64 毫秒。这一期把镜头转过来：**64 毫秒在你手上是什么概念？**

答案写在画布的参考带上：普通人的听觉加动作是 200–250 ms，优秀短跑选手的起跑反应能压到 120–180 ms。
也就是说，两台车之间那 64 毫秒的差距，比人手一次反应的三分之一还短。

---

## 为什么做这个

队里一直有个说法：发令之后车动得快，成绩就好。

但发令这件事本身有两段。第一段是信号传到人的脑子里，第二段是从人的手到释放机构。
CO₂ 车没有第一段，它靠机械释放。可第二段躲不掉——你按下按钮，到气针真的被捅开，中间照样有延迟。

做这个是为了把第二段的量级摆出来。五秒钟的测试，比讲十分钟课有用。

---

## 状态机

四个状态，加一条犯规分支：

```
idle ──点击──> armed ──灯亮──> lit ──点击──> result ──900ms──> idle
                 │
                 └──闪灯前点击──> foul ──1200ms──> idle
```

- `idle` 还没开始，或者上一次的点已经结算完
- `armed` 随机等 1.5–4.0 秒。**这段时间里点一下就是抢跑**
- `lit` 面板整块点亮成橙色，`performance.now()` 在这一刻打点
- `result` 显示刚才这一枪的时间，1 秒后自动回到 `idle`
- `foul` 面板换成深底加橙框，这一次直接判负，**不进样本，也不进平均**

抢跑之后不重来整轮，只废掉这一枪。连抢三次会显示「抢跑 3 次」，右上角那行数字是橙色。

跑满五次之后 `idle` 不再显示「点击开始」，面板换成判定板。

## 判定

面板左边的字由五次极差决定：

| 极差 | 判定 |
|---|---|
| ≤ 45 ms | 稳 |
| 46–90 ms | 一般 |
| > 90 ms | 波动大 |

右边把五次原始读数一字排开，最快的那次用橙色标出来。这样「平均 226」和「五次分别是 240/214/255/202/219」在同一块面板上，一眼能对上是哪一次拖了后腿。

平均落在哪个区间由参考带决定：

```
120–180 ms   优秀短跑起跑
200–250 ms   典型听觉反应
```

这两条区间以半透明横带的形式画在柱状图背景里，五根柱子直接压在上面。不用看数字也知道自己在什么位置。

## 默认这一组成绩

第一帧就要是一张完整的成绩卡，所以页面加载时会先灌一组固定样本：

```
第 1 次   240 ms
第 2 次   214 ms
第 3 次   255 ms
第 4 次   202 ms
第 5 次   219 ms

平均      226 ms
最快      202 ms
最慢      255 ms
极差       53 ms
判定      一般
区间      典型听觉反应 (200–250 ms)
```

**这五个数是我用固定种子生成的，不是人点出来的。** 见下面「已知问题」第一条。

种子是 `mulberry32(0x5EED)`，映射到 `196 + rand() × 62`，取整。换种子重跑会得到另一组，但同一台机器上永远一样——导出和截图才可复现。

## 一个必须写下来的发现

**随机延迟必须每次都不同，否则两轮之后就能背出节奏。**

第一版里整个程序只开了一个随机数发生器，种子 `0x5EED`，既用来灌预填样本，也用来算闪灯延迟。
写完之后我发现：**每次刷新页面，五枪的等待时间序列一字不差。**

这意味着练到第三轮，人是靠记忆而不是靠反应在点——测出来的数字会越来越好看，而且完全是假的。

改法是拆成两段：预填样本继续用固定种子（导出可复现），灌完之后立刻把种子换成 `Date.now() ^ Math.random()`。
现在每次刷新等待时间都不一样，门禁连跑两次分别等了 **2261 ms** 和 **2989 ms**，在同一份代码下。

这条不改的话，整个项目就是个骗人的仪器。它不报错，界面也正常，只是数字没有意义。

## 已知问题

这些是真的没做好的地方，不是客套。

1. **五条样本是我编的，不是人点出来的。** 无头浏览器里没人真的去点，但第一帧必须是一张填满的成绩卡，所以用固定种子灌了 240/214/255/202/219。这五个数没有任何生理意义。真实鼠标点击的反应时间通常落在 **250–350 ms**，比这组慢一截——因为真人的手指要移动、要按下、要等鼠标微动开关闭合。你在自己浏览器里点出来的数大概率不会是 226。

2. **测出来的不是「光子到肌肉」，是「重绘到事件回调」。** `performance.now()` 在 click 回调里取，中间隔着浏览器的事件派发；标签页忙的时候这一段能多出 10–30 ms。而且面板是在上一帧画出来的，用户实际看到的光比代码记录的 `litAt` 要早一个帧间隔。两个误差方向相反，但都没有被我量化过，所以这个数**偏乐观还是偏悲观我说不准**。

3. **参考区间是我读来的，没附出处。** 200–250 ms 和 120–180 ms 直接印在画布的参考带上，但代码和文档里都没有引用来源。这两个区间在文献里说法本来就不统一——听觉反应比视觉反应快 20–40 ms，简单反应比选择反应快得多。当成量级参考，不要当标准。

4. **判定阈值 45 / 90 ms 是我拍的。** 五次样本的极差本身就是个噪声极大的统计量，理论上该用标准差或者干脆多跑几次。53 ms 判成「一般」纯粹是因为我定了 45 这条线，把它挪到 55，同一组数据就变成「稳」了。

5. **五次太少了，统计上什么都说明不了。** 五次的平均值，标准误大概是极差的三分之一——按这一组算就是 ±18 ms 左右。想要靠得住的数字，20 次起步。选 5 次是为了适配一张竖版卡片的版面，不是统计需要。

6. **抢跑只判「闪灯前点击」，不判「提前预判」。** 如果有人踩着节奏提前一点点动，只要落在闪灯之后就会被如实记下——但那其实是预判，不是反应。真正的反应测试会在下端加一条 < 100 ms 的剔除线，我这里没有。所以理论上可以靠数拍子刷出很高的成绩。

7. **重新播种的时机没有断言保护。** 现在的顺序是「先用固定种子灌 5 条 → 立刻换成随机种子」，靠的是文件末尾那两行的先后关系。要是哪天有人改了预填条数又没注意，延迟序列会悄悄退回固定序列，界面上完全看不出来。代码里没有断言防这个。

## 目录

```
reaction-trainer/
├─ index.html          说明 + 三个只读读数 + 1080×1920 画布
├─ src/
│  ├─ main.js          状态机 + 绘图 + 测试钩子
│  └─ reel-export.js   导出模块（来自 shared/）
├─ dist/app.js         esbuild 打出来的 IIFE
└─ tests/
   ├─ gate.mjs         状态机断言 + 抢跑断言 + 安全区像素墨量/色彩
   ├─ visual.mjs       安全区死区检测、墨量统计
   ├─ fonts.mjs        豆腐块检测
   └─ ascii.mjs        画布转字符密度图
```

`src/reel-export.js` 是从 `_stemlab/shared/` 拷进来的，
**改项目里的会被下一次 `node build.mjs` 冲掉**，要改去改 shared 那份。

这个项目**没有用** `plot.js`。柱状图只有五根柱子加两条参考带，手画比套通用图表模块短，也省掉一层坐标换算。

**画布本身就是成片，同时也是玩游戏的那块屏。** CSS 把它缩到 540×960 只是为了在桌面一屏放得下，导出的永远是 1080×1920。

没有 `requestAnimationFrame` 循环：状态一变就整帧重画一次。这样导出的每一帧都完全可复现，不存在「截图正好落在动画中间」的问题。

## 跑起来

```bash
cd _stemlab/projects/reaction-trainer
node build.mjs
node tests/gate.mjs
node tests/visual.mjs
node tests/fonts.mjs
node tests/ascii.mjs
```

四道检查当前全绿：

```
GATE OK  |  竖版 150KB  封面 127KB  |  墨量 17.19%  115 色  |  样本 5/5  平均 226 ms  最快 202  最慢 255  抢跑 1 次不进样本  |  随机等 2989 ms 后闪灯，点击记 9 ms
安全区内 150px 死区: 无
安全区整体墨量: 17.19%
画质检查通过
```

`墨量 17.19% / 115 色` 是门禁直接用 `getImageData` 量安全区像素得到的，不是自己报的数。空脚手架一般在 1.4% / 16 色左右，所以 8% 和 48 这两个阈值能真的拦住空壳。

门禁里除了像素，还有一组本项目专属的断言：

- 默认样本数**正好是 5**，目标值也是 5
- 抢跑之后样本数和平均值**都不许变**，犯规计数必须是 1
- 平均值必须落在 150–600 ms
- 清空后样本数必须是 0
- 逐条灌 5 次后，平均值、最快、最慢、极差必须和手算一致（188 / 267 / 79）
- 满额之后再灌，样本数不许超过 5
- 随机延迟区间必须是 1500–4000 ms

最后两条是**真跑一遍状态机**，不是走注入接口：

- `arm()` 之后状态必须是 `armed`；等 ≤ 6 秒必须等到 `lit`；实测等待落在 1500–4200 ms；点击后样本数 +1、状态变 `result`、记下的毫秒数在 0–200 之间
- `arm()` 之后**立刻** `hit()`，状态必须是 `foul`、犯规计数 +1、样本数仍然是 0

第二条就是「抢跑要判负」这条需求的机器证明。它走的是和真人点击完全同一条代码路径。

## 操作

- 点画布（或按 <kbd>空格</kbd>）开始，等灯，灯亮立刻点
- 跑满 5 次出判定，面板右下角写着「再来一轮请点面板」
- 「清空重来」把五次和犯规计数一起清零
- 「导出 9:16」出 1080×1920 竖版

侧栏那三个读数是纯文本，给屏幕阅读器用的；画布里的数字才是成片。

## 附：ASCII 密度图是怎么改这一版的

开发环境没有能读图的模型，所以 `tests/ascii.mjs` 把画布按 40px 一格压成字符密度图。第一版跑出来是这样：

```
 440 |.-:::::::::::::::::::::....|
 480 |.-:+@::::::::::::::::::....|
 520 |.-:-::--=-:::::::::::::....|
 560 |.-::-::::::::::::::::::....|
```

左边 `-` 是状态面板那条 6px 橙色竖条，`+@` 是「一般」两个字，然后剩下 **18 格全是 `:`**——面板 870×216 只有左三分之一有内容，右边一大片是纯底色。

修法是把五次原始读数排到面板右半边（`五次读数 [ms]` 加上五个数字），改完之后：

```
 480 |.-:+@::::::::::-:-:-::-....|
```

右侧多了四段 `:-:-:-::-`，面板两端都有东西了。

同一张图还看出底部 `1332–1400` 有一条 90px 空带，于是给「判读」补了第五行，整段间距也从 30px 收到 30px 但腾出了位置。

`ascii.mjs` 在这个项目里比截图有用：它不告诉你字好不好看，但它会告诉你哪一块是空的。
